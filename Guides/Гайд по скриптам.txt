Создание и оформление функций

файлы с функциями(скрипты) создаются своими руками в папке gamedata\scripts и называются "имя_файла.script", нигде больше их регать не надо.
Следите за тем, что пишете в скриптах, произвольные символы вызывают вылет, свои комментарии оставляем так:
-- мой коммент

Для начала давайте разберем функции, и то как они выглядят:

function имя_функции ()
	тело_функции
end

если внутри функции идёт if, то должно стоять условие, потом идёт then
далее идёт действие, которое будет выполнено при успехе, можно сделать действие и при провале

любой if всегда заканчивается end, как и функция, например:

function имя_функции ()
	if db.actor then
		выдаем предмет
	end
end

в этой функции проверяется существование актора, так как может случится вылет если актора не будет, зависит от того где происходит запуск функции.

так же если требуется кучу раз сделать проверку на актора, то в начале файла делаем локальную переменную
local actor = db.actor

и тогда в проверках: if actor then
экономия места.

так же end необходим в циклах for

Аргументы функций
в функциях часто можно встретить подобное:
dialogs.relocate_item_section(db.actor, "wpn_pm", "in")

dialogs - dialogs.script

relocate_item_section это функция из dialogs.script, а (db.actor, "wpn_pm", "in") это аргументы этой функции

то есть, если вы откроете dialogs.script и найдёте функцию relocate_item_section, то увидите:
function relocate_item_section(victim, section, type)

и вместо (victim, section, type) мы при вызове указали (db.actor, "wpn_pm", "in")

Когда в функцию не нужно ничего передавать делаем function имя_функции()

В диалогах и логике:
первый аргумент это актор - главный герой, его клиентский объект
второй аргумент это нпс, в логике которого была вызвана функция, либо тот с кем мы ведем разговор - его клиентский объект

в оригинале диалоги не позволяют передать, что-то кроме актора и нпс, а вот в ОГСР есть поддержка передачи аргументов в функции, вызываемые из диалогов, например:
<precondition>my_script.test_func(123, true, nil, ...)</precondition>
<action>my_script.test_func(123, true, nil, ...)</action>

То есть в оригинале НЕЛЬЗЯ оформить action  так:
<action>dialogs.relocate_item_section(db.actor, "wpn_pm", "in")</action>

Если указать после аргументов ... , то в функцию будут переданы стандартные аргументы, типа:
pSpeakerGO1->lua_game_object(), pSpeakerGO2->lua_game_object(), dialog_id, phrase_id
(актор, нпс, диалог, фраза)
если этого не сделать, то стандартные аргументы не будут переданы.

То есть если мы хотим взаимодействовать с нпс, обязательно делаем два аргумента (actor,npc)
function my(actor,npc)
	actor:kill(npc)
end

В логике похожая ситуация, функции вызываются например через on_info:
on_info = %=new_fire%

передается актор и нпс, при этом сама функция должна выглядеть:

function new_fire(actor, npc)
	npc:set_item(object.fire1, npc:best_weapon(), 1 ,1)  
end

т.е. видим что актор не участвует, но если не указать второй аргумент, не важно как вы записали первый - это будет актор

Для передачи других аргументов в логике, например, чисел - оформляем функцию так:
function new_fire(actor, npc, p)
npc:set_item(object.fire1, npc:best_weapon(), p[1] ,p[2])  
end


в логике:
on_info2 = %=new_fire(4:1000)%

в аргументы добавился третий - p

далее оно само понимает куда подставить 4, а куда 1000



Закрепим, что функции внутри функции вызывются так:

function имя_функции ()
	имя_файла.функция()
end

С нпс в функциях можно взаимодействовать не только через диалог или логику

Для начала определим локальную переменную obj - это будет клиентский объект, с ней будем взаимодействовать через клиентские методы, т.е. функции класса game_object, под взаимодействием понимается примерно следующее:

obj:set_money( 65000 ) установить количество денег 
obj:set_character_rank(1000) установить ранг
obj:set_npc_position(vector():set(-152.0,-18.0,-144.3))
Эти методы были добавлены в ОГСР

--установка отношений
obj:set_relation(game_object.friend, db.actor)

Для этого нужно определить сам объект:
local obj = level_object_by_sid(6)   	 -- стори айди
local obj = level.object_by_id(id)		 -- клиентский айди(он не известен за ранее, так как при новой игре назначается рандомно)

и так вот применять:
obj:set_item(object.fire1, obj:best_weapon(), 10 ,1000) 

Есть ещё и серверные методы, обозначим как sobj.

определение серверных объектов:
local sobj = alife():story_object(6)	 -- стори айди

пример:
--убрать привязку к аи сетке
alife():use_ai_locations(sobj, false)
--удалить объект:

получение клиентского объекта по серверному, obj из sobj:

Исользование методов класса game_object при спавне нпс через скрипт

Когда мы спавним нпс, его клиентская сторона образуется не сразу и использование методов класса game_object, т.е. клиентских приведет к вылету, поэтому есть такой вот способ, как без сейвлоадов сразу использовать клиентские методы на нашем нпс:
function spawn()
  local sobj = alife():create("my_test_stalker",vector():set(-152.0,-18.0,-144.3),98126,45)
  level.client_spawn_manager():add(sobj.id, 65535,
    function (id, obj)
      obj:set_goodwill(-5000, db.actor)
    end
  )
  return obj
end
Есть ещё нюансы, нпс должен быть  на расстоянии не более 140 метров от гг, иными словами в онлайне.

В данной функции указываются координаты и секция вашего нпс, всё как обычно, а вот взаимодействие может быть разным, тут:
obj:set_goodwill(-5000, db.actor)
изменение отношения этого нпс к актору, параметр obj передаётся за счёт
function (id, obj)
поэтому структуру не менять, а само взаимодействие с obj можно сделать так:
utils.send_to_nearest_accessible_vertex(obj,107814)
то есть передаём как удобно.


Получение объекта заспавненного через скрипт

Таким образом определить нпс:
local sobj = alife():object("esc_wolf")
не получится, так как их имя секции превращается в "esc_wolf12445", т.е. к нему добавился айди, который заранее неизвестен

Для определения клиента:
function perebor_obj()
	for a=1,65535,1 do
	local obj=level.object_by_id(a)
		if obj and string.find(obj:name(),"esc_wolf") then
			-- действие, например, убить этого нпс:
			obj:kill(obj)
		end
	end
end

Для сервера:
function perebor_sobj()
	for a=1,65535,1 do
	local sobj=alife():object(a)
		if sobj and string.find(sobj:name(),"esc_wolf") then
			-- действие, например, удалить этого нпс:
			alife():release(sobj, true)
		end
	end
end

Пример:

[logic]

Функции проверки должны лежать в \gamedata\scripts\xr_conditions.script

Методы в функция\оптимизация

В некоторых скриптах можно увидеть такие моменты:
level.client_spawn_manager

и конечно же никакого файла level.script нет, а если и есть, то функции client_spawn_manager в нем точно нет, это так называемый движковый метод, большинство описано в lua_help.script

Для быстродействия рекомендуется функции, использующиеся внутри файла оформлять как локальные:
local function нейм ()
***
end

такие функции могут быть вызваны только внутри файла где лежат.

Также немало важно использовать локальные переменные:
local test = 0

таким образом во всех функциях скрипта - test будет равен 0

всё это для оптимизации.

Используется это например так, в диалоге будет вызываться функция esc_timer, которая использует метод level.add_call(func1,func2), который при выполнении условий функции 1, выполняет функцию 2. В данном примере функция 1 это пародия таймера, и когда он сработает будет выполнена функция 2, которая убивает нпс по стори айди.

function esc_timer()
   local iTimer = time_global() + 10*1000
   local function check_timer()
            return time_global() > iTimer
   end
   local function kill_npc()
            local obj = level_object_by_sid(6)
            obj:kill(obj) 
   end
   level.add_call(check_timer, kill_npc)
end

Эти локальные функции можно вынести из функции esc_timer(), но можно оформить всё иным образом

function esc_timer()
   local iTimer = time_global() + 10*1000
   level.add_call(function()
                     return time_global() > iTimer
                  end,
                  function()
                  local obj = level_object_by_sid(6)
                     obj:kill(obj) 
                   end)
end

это использование безымянных функций.

ещё иногда можно встретить вызовы функций, в которых не указан файл скрипта, это нормально  когда функция локальная, либо в принципе находится в файле из которого вызывается, но если ничего из этого тогда эта функция из глобального пространства Луа _G
выглядит красиво и компактно, но это лишняя нагрузка, лучше не лениться.

В дополнение к таблице _G: Если через кейлоггер или еще как-то вызвать команду _G[имя скрипта] = nil, то движок вновь перекомпилирует указанный скрипт при первом к нему обращении. Что это дает? Это дает то, что если вы отлаживаете какой-либо код, то нет необходимости делать сейв/лоад после каждой правки. Если мы, допустим, правим файл amk.script, то достаточно после сохранения правок через кейлоггер вызвать

_G.amk = nil

и все - движок перекомпилирует его по новой и все изменения тут же вступят в силу без очередного сейв/лоада. Жаль, что эту фичу я для себя открыл только сейчас. Сколько времени можно было бы сэкономить.

Это работает для всех файлов кроме биндеров. Дело в том, что для каждого объекта биндер зачем-то компилируется отдельно, поэтому чтобы увидеть изменения, например в bind_monster.script, то нужно написать _G.bind_monster = nil и заспавнить нового монстра. И на новом объекте изменения уже будут применены.

Оформление функций для проверки
--------------------------------------------------------------------------------------------------------------

function название_функции()
	if "набор условий" then
		return true
	else
		return false
	end
end

"набор условий" это нечто вроде if has_alife_info("инфопоршн1") and not has_alife_info("инфопоршн2") then 
то есть, если получен "инфопоршн1" и не получен "инфопоршн2", то истина

или if sak.have_item_namber("af_medusa",1) and sak.have_item_namber("wpn_pm",1) then что означает, если получен 1 "af_medusa" и 1 получен "wpn_pm", то истина


ещё можно оформить так:

function timer()
  if "набор условий" then
    return true
  end
  return false
end

Разницы нет, можно использовать любой.

local con = nil -- переменная для объекта консоли
local con_command = "mm_net_player_name" -- консольная команда
local def_value = "_" -- значение по умолчанию - символ подчеркивания
 
function update()
	if not con then -- инициализируем схему
		con = get_console() -- кешируем консоль
		con:execute( con_command .." ".. def_value ) -- инициализируем дефотлным значением, т.к. кнопка не нажата
		for k,v in pairs(_G[script_name()]) do -- перебираем функции в текущем файле
			 -- v это функция 	и её имя является кодом клавиши
			if type(v)=='function' and DIK_keys[string.upper(k)] then
				local key = "k"..string.gsub(k,"dik_","") -- формируем ключ и
				con:execute("bind_console "..con_command.." "..k.." "..key) -- биндим кнопку на него
			end
		end
	else
		-- получаем из консоли значение параметра для нашей команды
		local str = con:get_string(con_command) 
		-- если оно не является значением по умолчанию
		-- и в этом файле есть функция с таким именем, то выполняем её
		if str~=def_value and this[str] then
			this[str]()
			con:execute(con_command.." "..def_value) -- записываем значение по умолчанию
		end
	end
 
end

В function proceed() в файле \gamedata\scripts\escape_tasks.script
там запущена постоянная проверка на соблюдение условий, полезно, когда нужно чтобы условие проверялось вне квеств и диалога.
Начало файла: 
function proceed()
 вставляем
	if	not has_alife_info("tutorial_artefact_start") and sak.have_item_namber("af_medusa",1)
	then		
		db.actor:give_info_portion("tutorial_artefact_start")
	end

Разбираем: проверка будет работать пока не получен инфо "tutorial_artefact_start", так как после попадания в инвентарь "af_medusa" будет выдан инфо "tutorial_artefact_start" тем самым завершит проверку.

Свои проверки так же начинаем с if и заканчиваем end, оформляем по принципу:
	if "набор условий" and not has_alife_info("инфопоршн1") then
		-- ваше действие
		db.actor:give_info_portion("инфопоршн1")
	end

"набор условий" это нечто вроде if has_alife_info("инфопоршн1") and not has_alife_info("инфопоршн2") then

то есть, если выполнено условие и не получен инфо, то выдаем этот инфо чтобы закрыть проверку, если так не сделать, то "ваше действие" будет выполнятся бесконечно, такой проблемы лишены квесты и прекондишены в диалогах, ведь там если истина, то сразу функция выключается

function is_night()
